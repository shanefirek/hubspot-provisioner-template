## TL;DR

A real multi-tenant HubSpot provisioner — Public App + OAuth callback server + Postgres-backed portal store + a clean 5-step provisioning pipeline (Lists → Properties → Lead Status → Workflows → Dashboards). Architecture is solid. The portability gap is that **the *spec* (what gets provisioned) and the *driver* (how it gets provisioned via HubSpot) are fused into the same JS modules**, so porting this pattern to Salesforce/Attio requires rewriting it, not swapping a driver. Headline refactor: extract the provisioning content into a declarative spec (`spec/contacts.yml`, `spec/workflows.yml`), make each `provisioning/*.js` a thin driver that consumes it. Once that's done, the Salesforce and Attio equivalents become driver implementations against the same spec.

---

## Classification

- **Primary tier:** Tool (server-style — runs as a deployed service, not a CLI)
- **Reasoning:** `server/src/index.js` is an Express app with OAuth callback + REST routes; `server/src/provisioning/index.js` is a pure pipeline of API mutations; no LLM calls, no prompts, no agent logic. The `hubspot-app/` subdir is the HubSpot Public App definition (`hsproject.json`, `app-hsmeta.json`) — adjacent infra, not part of the runtime code.
- **Hybrid smell?** Mild. The server *is* the tool — `app.listen()` in something that conceptually performs "provision a portal" pushes it toward a long-running service shape when a CLI invocation per portal might be cleaner. But the OAuth callback genuinely needs to be a web server, so this is justified.

## Strengths

1. **The STEPS pipeline pattern** (`server/src/provisioning/index.js:10-16`) is excellent — clean, ordered, each step receives a context object that subsequent steps merge into. This is the right shape and should be preserved across CRM drivers.
2. **Idempotency is taken seriously** (`provisioning/properties.js:172-181`, `upsertPropertyGroup` GET-after-POST). 409s are expected, handled, not fatal. Re-running on an existing portal is safe.
3. **Honest acknowledgement of portal-specific constraints** (`workflows.js:7-11`) — comments call out that two workflows are created disabled because they depend on portal-specific lists. This kind of in-code documentation of edge cases is exactly right.
4. **OAuth-based multi-tenancy** — portals are first-class citizens. No environment forks per client.
5. **The `runProvisioning` results array** returns a structured per-step status — this is the right output shape for machine callers.

## Findings

### P0 — Blockers to portability (must fix before reusing the pattern for Salesforce/Attio/etc.)

**P0-1: Spec is fused with driver.**
- **Where:** `server/src/provisioning/properties.js:5-158` (`CONTACT_PROPERTIES` array), `provisioning/workflows.js:13+` (`WORKFLOW_DEFINITIONS`), `provisioning/lists.js`, `provisioning/dashboards.js`.
- **Why it matters:** Cannot port this template to Salesforce without rewriting 1,000+ lines of HubSpot-shaped JSON. The pattern is right; the *content* is locked into one CRM's API shape.
- **Fix:** Introduce `spec/` at the root with declarative YAML/JSON:
  - `spec/contacts.yml` — properties as a CRM-neutral list (`name`, `label`, `type`, `options`, `description`)
  - `spec/lists.yml` — list definitions
  - `spec/workflows.yml` — workflow intent in plain language (trigger condition, action, why); the HubSpot driver compiles this into Flow Builder JSON
  - `spec/dashboards.yml` — dashboard intent
  Then each `provisioning/*.js` becomes a thin driver: read spec → translate to HubSpot API calls.

**P0-2: No top-level README.**
- **Where:** `~/projects/hubspot-provisioner-template/`
- **Why it matters:** The front door is missing. Anyone (including future Shane) opening this repo has no idea what it is or how to run it.
- **Fix:** Top-level README with: what this is in one paragraph, the four moving pieces (HubSpot Public App, OAuth callback server, Postgres, provisioning pipeline), a quick-start, and a link to per-component docs.

**P0-3: No LICENSE.**
- **Where:** Top level.
- **Why it matters:** If Shane plans to re-template this for clients, licensing ambiguity is a real blocker.
- **Fix:** Add MIT (or chosen license).

### P1 — Best-practice gaps

**P1-1: No `--dry-run` mode.**
- **Where:** `routes/portals.js` (HTTP entry), `provisioning/index.js` (pipeline).
- **Fix:** Add a `dryRun` boolean threaded through `runProvisioning(accessToken, { dryRun })`. Each step should support a "preview what would be created" mode that hits the HubSpot read APIs but skips mutations.

**P1-2: No tests.**
- **Where:** No `tests/` or `*.test.*` files.
- **Fix:** At minimum, contract tests against the HubSpot API client mock — verify the property/workflow payload shapes don't drift. Snapshot tests on `WORKFLOW_DEFINITIONS` would catch accidental schema changes.

**P1-3: Versioning/release hygiene.**
- **Where:** `server/package.json` is at `1.0.0` with no CHANGELOG.
- **Fix:** Tag the initial commit, start a CHANGELOG, bump versions on every provisioning-content change so portals can be traced to a spec version.

**P1-4: Unstructured logging.**
- **Where:** `console.log` throughout `provisioning/*.js`.
- **Fix:** Replace with a `logger` module that supports `--output json` mode for machine consumers.

### P2 — Nice-to-haves

- **P2-1:** A CLI wrapper (`bin/provision-portal`) that wraps `runProvisioning` for testing against a single portal locally without going through OAuth. Speeds iteration.
- **P2-2:** A `POST_PROVISION_VERIFY` route that re-reads portal state and reports drift from the spec. Useful for confirming a fresh install or detecting manual portal edits later.
- **P2-3:** Consolidate `AGENTS.md`, `CLAUDE.md`, `HUBSPOT_PROJECTS.md` in `hubspot-app/` — there's overlap. Pick one canonical doc.

## GTM-stack fit

- **Tier in the four-tier model:** Tool (server-shaped).
- **What plays should call it:** `/setup-new-client` in `gtm-agent/` — when onboarding a new client, this is the first thing it should invoke (assuming HubSpot is the CRM).
- **What it should call:** Nothing directly. Pure HubSpot API consumer.
- **Relationship to `gtm-agent/`:** External tool. Should remain a separate repo. `gtm-agent/` references it as a deployed service URL or local invocation.
- **Slash-command opportunity:** `/provision-crm` in `gtm-agent/` that:
  1. Reads `${CRM_PROVIDER}` from client config
  2. If `hubspot`, calls this server's `/api/portals/:id/provision` route
  3. If `salesforce` or `attio`, calls the equivalent provisioner (once they exist)
  This is the canonical example of the spec-vs-driver separation paying off.

## Verdict

The architectural bones are right — pipeline, idempotency, multi-tenancy. **But it's not portable to other CRMs without a refactor**: the provisioning content is JS-shaped, not data-shaped. Before you build the Salesforce or Attio equivalents, do P0-1 (extract spec → driver). That single change is worth a week of work because it makes every subsequent CRM driver a pattern-match instead of a from-scratch build, and it gives you a `git diff`-able artifact for "what is a GTM-ready CRM" that lives independently of any vendor's API. After P0-1, ship the top-level README and LICENSE. Tests and CLI wrapper can wait. **Single most important next move: extract `CONTACT_PROPERTIES` and `WORKFLOW_DEFINITIONS` to `spec/*.yml`, refactor `provisioning/*.js` to consume the spec.**
