We deployed the server to Railway, registered the Public App in HubSpot, created a Developer Test Account, and ran the OAuth install end-to-end. The first install partially failed (one ✗ on a list creation). Two real bugs were found, fixed, and verified by re-provisioning. ## What changed since v1

### Bugs found in live execution (not visible from static read)

**Bug 1 — STEPS dependency order violation (P0, fixed)**
- **Where:** `server/src/provisioning/index.js:10-16`
- **Symptom:** First install returned `✗ Lists` with HubSpot error `The following properties did not exist for the object: dnc_status`.
- **Root cause:** The STEPS pipeline had `Lists` before `Properties`. The `Do Not Contact (Individual)` list filter references the custom `dnc_status` property, which doesn't exist on the portal until `Properties` runs. Domain DNC succeeded because it only uses HubSpot-standard properties.
- **Fix applied:**
  ```js
  const STEPS = [
    { name: 'Properties', fn: createProperties },
    { name: 'Lead Status Options', fn: ensureLeadStatusOptions },
    { name: 'Lists', fn: createLists },
    { name: 'Workflows', fn: createWorkflows },
  ];
  ```
- **Status:** Verified by re-running provisioning; Lists step now passes.

**Bug 2 — `dnc_status` filter uses wrong operationType (P0, fixed)**
- **Where:** `server/src/provisioning/lists.js:86`
- **Symptom:** After fixing Bug 1, Lists failed again with `The property dnc_status with type enumeration cannot be used with property operation type: BOOL.`
- **Root cause:** `dnc_status` is defined in `properties.js:28-37` as `type: 'enumeration'` with values `'true'`/`'false'` (HubSpot's idiomatic "boolean checkbox" — enumeration property displayed as a checkbox). But the list filter used `operationType: 'BOOL'` with `value: true`. HubSpot returned the valid operation types: `[TIME_POINT, ENUMERATION, ALL_PROPERTY, TIME_RANGED, COMPARATIVE_PROPERTY_UPDATED]`.
- **Fix applied:**
  ```js
  filters: [{
    property: 'dnc_status',
    operation: {
      operator: 'IS_ANY_OF',
      includeObjectsWithNoValueSet: false,
      values: ['true'],
      operationType: 'ENUMERATION'
    },
    filterType: 'PROPERTY'
  }],
  ```
- **Status:** Verified — Lists step now creates all 3 lists cleanly.
- **Note:** The same enumeration-as-boolean pattern is used for `call_list` and `sdr_status` (originally `tam_*`; renamed 2026-05-27 for naming hygiene) in `properties.js`. Those aren't filtered on in any list, but if they ever are, the same `ENUMERATION` operationType must be used.

**Bug 3 — `dashboards.js` was an empty stub reporting ✓ (P1, fixed)**
- **Where:** `server/src/provisioning/dashboards.js` (entire file)
- **Symptom:** Every install reported `✓ Dashboards`, but no dashboards were created. Misleading success signal.
- **Root cause:** `createDashboards` was an empty function body with `// TODO`. The STEPS pipeline included it.
- **Fix applied:** Removed `Dashboards` entry from STEPS array. Deleted `dashboards.js`. If/when real dashboards are needed, add a new step with actual implementation.
- **Status:** Re-provision now reports 4/4 ✓ honestly.

### v1 findings invalidated

**v1 P0-4 — `eventTypeId: '4-655002'` was claimed to be portal-specific (NOT TRUE)**
- **Original claim:** Three EVENT_BASED workflows reference `eventTypeId: '4-655002'`. The audit assumed this was a portal-specific custom event ID and that the workflows would either fail to create or be inert on a fresh portal.
- **What we actually observed:**
  - All workflows created successfully.
  - The ID was stored as-is post-creation (HubSpot did NOT translate it).
  - We then manually triggered the dependency: created a contact with `hs_lead_status=NEW, lead_origin=website`, waited 5s, updated `os_last_sent_time` to current timestamp, waited 90s.
  - Re-read the contact: `hs_lead_status` had flipped to `IN_PROGRESS`. **The workflow fired.**
- **Conclusion:** `4-655002` is a HubSpot **standard event type** (likely "contact property update"), portable across all portals. The v1 concern was incorrect.
- **However:** This is still worth a fix — `eventTypeId` as a magic number is fragile. The right move is to either (a) document what `4-655002` represents with a code comment, or (b) replace it with a constant that has a self-documenting name (e.g., `HUBSPOT_EVENT_PROPERTY_UPDATE = '4-655002'`).

### v1 findings still standing

- **P0-1 (spec/driver fusion)** — confirmed still the right call. We just fixed two pure-content bugs (step order + filter type) that would have been compile-time-detectable if the provisioning content were declarative YAML with schema validation. Cost of imperative-JS-as-spec: silent runtime breakage on fresh portals.
- **P0-2 (no top-level README)** — still missing.
- **P0-3 (no LICENSE)** — still missing.
- **P1-1 (no `--dry-run` mode)** — still missing. Worth flagging that we found Bug 1 + 2 by re-running against a live portal; a dry-run mode would have surfaced them locally without paying for a test portal.
- **P1-2 (no tests)** — confirmed. A simple snapshot test on the request payloads to HubSpot would have caught Bug 2 (BOOL vs ENUMERATION mismatch) because the property type and the filter type are in two different files.
- **P1-4 (unstructured logging)** — confirmed. Pulled Railway logs to debug; they're plain `console.log` output. Fine for one-portal debugging, painful for multi-tenant troubleshooting.
- **P2-1 (CLI wrapper for single-portal testing)** — would have saved 20+ minutes of redeploy cycles during this debug session.

## Repo structure decision (post-audit cleanup)

We initially deployed the personal Railway environment from `~/projects/hubspot-provisioner-template/` directly and committed deployment-specific URLs into the template. That's wrong — a template should stay deployment-agnostic.

**Cleanup applied:**

1. **Forked the deployed state into a new personal repo.**
   ```
   ~/projects/hubspot-provisioner-template/   ← clean template, your-domain.com placeholders
   ~/projects/hubspot-provisioner-personal/   ← personal deployment, real Railway URLs
   ```
2. **Reverted the URL config commit (`4c7a318`) in the template** with a non-destructive revert commit (`132119c`). The bug fixes (`bf94cc8`) and `.gitignore` (`d083a80`) stay — those apply to every deployment.
3. **Unlinked Railway from `template/server`.** Only `personal/server` is linked to the Railway project now, so `railway up` from the template fails safely with "No linked project found." No way to accidentally deploy the placeholder-state template to the live Railway.

**Implication for future deployments (Shane's pattern going forward):**

```
hubspot-provisioner-template/      ← upstream source of truth
├── (universal bug fixes land here first)
└── (no Railway URLs, no Client IDs, no env-specific config)

hubspot-provisioner-personal/      ← Shane's deploy (current)
├── (forks template at the relevant commit)
├── URL config for hubspot-provisioner-server-production.up.railway.app
└── Railway-linked to project d40b46ae-...

hubspot-provisioner-{client}/      ← future client deploys (one per)
├── (forks template at the relevant commit)
├── URL config for THEIR Railway URL
└── Railway-linked to a different project under THEIR Railway team
```

The longer-term fix is what `v2 P0-2` proposed: env-driven URL substitution at build time. That'd let the template stay literally identical across deployments — only env vars differ. Real refactor; not done in this session.

**Concrete next step from here:** any future provisioning bug fix → land in `template` first, cherry-pick or merge into `personal`. Any deployment-specific change → personal only.

## Verdict (updated)

The provisioner works. We watched it create 17 properties, 6 lead-status options, 3 lists, and 6 workflows on a fresh test portal, and verified one of the EVENT_BASED workflows actually fires when its enrollment criteria is satisfied. Two bugs that would have blocked any first install were found and fixed during this audit. The architectural concerns from v1 (spec/driver fusion, missing README/LICENSE, no tests, no dry-run) all still stand and are still the right things to address before this gets installed on anyone else's portal — but the *core thing actually does the thing it says it does*. That's a meaningful step up from "we read the code and it looks reasonable."

**Single most important next move:** commit the fixes, then add a `--dry-run` mode so the next install attempt doesn't repeat the redeploy-debug cycle we just did.
